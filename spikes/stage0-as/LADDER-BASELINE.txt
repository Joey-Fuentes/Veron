# LADDER-BASELINE -- known-good artifacts of the ladder, native aarch64.
#
# WHY THIS FILE EXISTS. stage0-as is about to be modified (b.gt/b.le, the sf
# bit, shifted-register operands, input rejection). Any of those changes the
# BYTES of stage1 and stage2, because both use the affected forms:
#
#     mov  W i     57 uses      cmp  W i     39 uses      mov  W X   14 uses
#     ldrb W X X  162 uses      str  W X     86 uses      ldr  W X   64 uses
#
# So "did the ladder still build?" is not the question -- it will build, and it
# will build DIFFERENT. The question is whether it still MEANS the same thing.
# A bare byte-compare against this file answers the first; the emitted-assembly
# comparison in the same workflow step answers the second.
#
# HOW TO UPDATE. When a change to stage0-as is intended to move these bytes,
# update the line in the SAME commit and say in the message which forms moved
# and why. A baseline edited separately from the change it describes is a
# baseline nobody reads.
#
# Values are sha256, first 16 hex chars, from the green stage3-hermetic-arm64
# run of 2026-07-27 (job 82026046700) -- the run where 426/426 passed, the canon
# fixpoint held, and G1 matched upstream's M2-Planet byte for byte.
#
# format:  <name> <bytes> <sha256[0:16]>

# stage0-as MOVED on 2026-07-27, commit 49d5db3, intentionally: input
# rejection plus the b.gt/b.le condition fix, +40 instruction lines and two
# message strings. 6248 -> 6640 is larger than 40 instructions because `ld`
# also carries seven new symbol-table entries. The line below was updated in
# that change's own follow-up, and the evidence that it is safe is on the same
# run: elf, stage1, stage2 and all eight emitted-output fingerprints were
# UNCHANGED, and stage3-hermetic-arm64 on the same commit passed 426/426 with
# G1 == dc38e13e4ceaeecb.
# 6760 -> 6768 at the bss_origin change (r26). The +8 bytes are an ELF symbol
# table entry, NOT code: .text is untouched, all 695 instructions are identical,
# and the round-trip proves it -- 100% against binutils 2.47 AND llvm-objdump
# 22.1.8, with the two decoders agreeing on all 696 words. I had said this
# change "provably can't" move stage0-as's bytes; that was wrong. Adding a
# symbol grows the file even when it changes no instruction.
# 6768 -> 6864 when the .ascii strings moved to .rodata (r41), which is
# what made .text pure code and the round-trip total.
# 7792 -> 7848: two-character labels (sym_idx) so the source's 103 labels fit
# a symbol table that only had ~90 usable single-character slots.
# 7848 -> 7920: h_mov now encodes the UPPER halfword. MOVZ carries 16 bits and
# a 2-bit shift, and only the low halfword was being set -- so all 29 constants
# over 16 bits (0xd2800000, INBUF_SZ, the opcode words) silently assembled as
# `mov Rd, #0`. The probe never saw it because it substituted #8 for an
# immediate; the self-host gate found it on its first real run.
#
# WITH THIS, SELF-HOSTING IS PROVEN: gen1 == gen2 == gen3 (3328 bytes,
# 18a1c7e0004359bb) and gen1 builds stage1 byte-identically to the reference
# build. The four words differing from as+ld are all .bss references, which
# ld page-aligns and elf does not.
# 7920 -> 8144, two changes measured on the same run:
#   r68  ldr/str gained an OPTIONAL unsigned immediate offset. h_ls_off is a
#        tail both handlers now share, scaling by 8 for the x-form and 4 for
#        the w-form. Added for `elf`, not for this file -- elf.aarch64.s uses
#        it four times and could not be translated without it.
#   r71  `movn`, the negative-immediate move. AArch64 has three moves and this
#        language already spelled two of them separately, so movn completes the
#        set rather than teaching `mov` to pick an encoding from the VALUE --
#        which is the one thing the seed rules forbid an assembler to do. It
#        shares hm_fold with `mov`; the two differ only in the base word, and a
#        second copy of that fold is a second place for the halfword bug above
#        to come back. elf's AT_FDCWD (#0xffffffffffffff9c) needed it: the
#        translator inverts to `movn x0 99`, because parse_dec accumulates in a
#        w register and cannot hold the 64-bit form.
# 817 -> 833 instruction lines, and the rest of the growth is symbol and string
# table entries for five new labels, not code.
#
# WHY THIS IS SAFE, all from the run that produced these numbers: the plain diff
# of canonical source against canonical disassembly is IDENTICAL over 942 lines;
# both decoders agree 833/833; both reassemble the .text exactly; the whole
# binary reconstructs to 8144 bytes matching; gen1 == gen2 == gen3; gen1 still
# builds stage1 byte-identically; and all EIGHT emitted-output fingerprints
# below are unchanged. The ladder uses neither new form, so nothing it produces
# could move -- and nothing did.
#
# BOTH FORMS ARE NOW PROBED, which they were not when r68 landed. The generator
# used to emit cases only for forms THIS file uses, but stage0-as consumes the
# .s0 translation, and that is a different language -- a form can exist in .s0
# and in no .s anywhere. r71 made it probe every DOCUMENTED form: 58 pairs,
# 58 ok, 0 wrong bytes, 0 rejected, with the bench model agreeing on all of
# them. The five forms this file does not itself use show a count of 0, which
# is the honest number rather than a missing row.

# checked by the self-host gates (gen1 == gen2 == gen3, elfgen1 == elfgen2 ==
