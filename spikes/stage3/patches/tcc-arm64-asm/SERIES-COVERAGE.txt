0006-tccgen-convert-long-double-constants-when-cross-compiling.patch
    NOT PART OF THE FEBRUARY SERIES. Ours, found while chasing a printf("%f")
    that produced 8.000000 for 5.008 in the stage3-to-stage4 bridge.

    init_putv picks how to emit a long double constant by comparing SIZES, and
    x86_64 and arm64 both have sizeof(long double) == 16 with completely
    different formats -- x87 80-bit versus IEEE binary128. A cross-compiling
    tcc therefore memcpy's host x87 bytes into a binary128 slot, and every
    long double constant in the program is silently wrong. f3_unpack then
    reads the exponent from the wrong word, finds 0, and __trunctfdf2 returns
    ZERO for every value.

    Measured and fixed locally: x86_64 host, arm64 target, output verified
    under spikes/toolbox/qemu-aarch64-static.

        (double)5.008L   before 0x0000000000000000   after 0x4014083126e978d5
        (double)1.5L     before 0x0000000000000000   after 0x3ff8000000000000

    THIS IS PROBABLY NOT THE BRIDGE'S BUG. The bridge builds on a NATIVE arm64
    runner, where sizeof matches AND the formats agree, so the guard is false
    and the original path is taken unchanged. It is a real tcc bug on the
    cross path and worth carrying and reporting, but the vfprintf.c miscompile
    measured in CI -- swap one gcc-built object and every value is correct --
    is a separate fault still to be found.


0007-tccgen-gvtst_set-must-not-fold-a-register-as-a-constant.patch
    OURS. The bug that actually stopped the bridge at perl.

    `if (some_long_double)` was always FALSE. Every explicit comparison was
    correct -- ==, !=, <, >, <=, >= all pass -- and only the implicit truth
    test failed, which is what made it look like a comparison bug for several
    rounds when it is not one.

    gvtst_set assumed that if gen_op does not leave VT_CMP it "must be
    VT_CONST then" and read vtop->c.i. On arm64 a long double comparison
    calls __netf2 and csets the result, leaving a real INTEGER REGISTER --
    neither. c.i was then the constant field of a register-resident value,
    in practice zero, so the condition folded to a compile-time false and no
    branch was emitted at all:

        bl __netf2 ; cmp w0,#0 ; cset w0,ne ; nop ; mov w0,#0

    musl's fmt_fp is built on `for (; y; y = ...)` loops, so no float was
    ever formatted: printf("%.6f", 5.008) gave 8.000000, the exponent alone.

    0006 AND 0007 ARE BOTH NEEDED, measured on a clean tree: 0007 alone fixes
    if(A) but leaves !Z wrong, because that needs 0.0L to be a correct
    constant, which is 0006. Together all thirteen cases in the local test
    pass.

    Verified with an x86_64-hosted arm64 tcc under
    spikes/toolbox/qemu-aarch64-static. Regression-tested against if() on
    int, long, double, float, pointer, function call, &&, ||, while(). tcc's
    own `make test` passes, including ret_longdouble_test and stdarg_test.

    STILL UNVERIFIED: whether this is the bridge's bug. The one-file swap in
    CI showed that a gcc-built vfprintf.o fixes everything, which is
    consistent -- but the bridge builds NATIVELY on arm64 where 0006 is inert,
    so if 0007 alone is enough there, it will show in the next reference run.
